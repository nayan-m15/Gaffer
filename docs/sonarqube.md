# SonarQube (code quality + coverage)

This project analyses code with a **self-hosted SonarQube (Community
Edition)** instance. It reports bugs, code smells, security hotspots,
duplication, and test coverage for the backend (coverage) and frontend
(static analysis only — no frontend tests exist yet).

CI runs the scan automatically; this doc covers the one-off setup needed
before that works, and how to run a scan locally.

## How it fits together

- [`sonar-project.properties`](../sonar-project.properties) — project key,
  source/test paths, exclusions, and where the coverage report lives.
- [`docker-compose.sonarqube.yml`](../docker-compose.sonarqube.yml) — spins
  up SonarQube Community Edition + its Postgres database. Run this on
  whatever server will host the permanent instance (or locally to try it
  out). It is **not** part of the app's own runtime stack.
- `.gitea/workflows/test.yml` — the `sonarqube` job installs backend deps,
  runs `npm --prefix backend run test:cov` (Jest coverage → `backend/coverage/lcov.info`),
  then runs the official `SonarSource/sonarqube-scan-action`.
  - It only runs on **push to `main`/`develop`**, not on pull requests.
    SonarQube Community Edition doesn't support multi-branch analysis or PR
    decoration (that requires a paid edition, or SonarCloud) — scanning every
    PR would just repeatedly overwrite the main-branch analysis, so it's
    disabled to avoid confusing results.

## What you need to configure

### 1. Stand up the SonarQube server

Pick a machine that stays up (the university server, or wherever else makes
sense — it does **not** need to be the same box as Gitea, it just needs to be
reachable from your Gitea Actions runner):

```sh
docker compose -f docker-compose.sonarqube.yml up -d
```

Open `http://<that-host>:9000`, log in with the default `admin` / `admin`,
and set a new password when prompted.

> First boot can take a minute or two (Elasticsearch warm-up). If it exits
> immediately on Linux, you likely need to raise `vm.max_map_count`:
> `sudo sysctl -w vm.max_map_count=262144`.

### 2. Create the project

In SonarQube: **Projects → Create Project → Manually**.

- Project key: `sport-coaching-tool` (must match `sonar.projectKey` in
  [`sonar-project.properties`](../sonar-project.properties))
- Display name: `Sport Coaching Tool`
- Choose **"Locally"** / **"Use the global setting"** for analysis method
  (we're driving it from CI, not Sonar's own CI integration wizard).

### 3. Generate a token for CI

**My Account → Security → Generate Token.**

- Name: something like `gitea-ci`
- Type: **Project Analysis Token**, scoped to `sport-coaching-tool`
  (safer than a global user token — CI only needs to submit analyses for
  this one project)
- Copy the token now; it's shown once.

### 4. Add Gitea Actions secrets

In the Gitea repo: **Settings → Actions → Secrets**, add:

| Name | Value |
| --- | --- |
| `SONAR_TOKEN` | the token from step 3 |
| `SONAR_HOST_URL` | e.g. `http://<your-sonarqube-host>:9000` |

Both are read by the `sonarqube` job in `.gitea/workflows/test.yml`.

### 5. Quality gate (optional but recommended)

SonarQube ships a default "Sonar way" quality gate. If you want the CI step
to fail the build when quality drops, no extra config is needed — the scan
action already checks the quality gate status after analysis. Adjust gate
conditions under **Quality Gates** in SonarQube if the defaults are too
strict/loose for this project.

### 6. Confirm it works

Push to `main` or `develop` (or merge a PR), then check the `sonarqube` job
in the Gitea Actions run and the project dashboard in SonarQube. First run
populates the baseline; subsequent runs show new-code metrics against it.

## Running a scan locally (optional)

You don't need anything installed beyond Docker — run the official scanner
image against your local checkout:

```sh
npm --prefix backend ci
npm --prefix backend run test:cov

docker run --rm \
  -e SONAR_HOST_URL="http://host.docker.internal:9000" \
  -e SONAR_TOKEN="<your token>" \
  -v "$PWD:/usr/src" \
  sonarsource/sonar-scanner-cli
```

On Linux, replace `host.docker.internal` with the host's actual address (or
add `--network host`) if the SonarQube instance is running locally too.

`test:cov` automatically normalizes LCOV source paths to repository-relative
paths such as `backend/src/app.controller.ts`, including on Windows, so the
scanner can resolve the same report from the repository root on every platform.

## Coverage scope note

Only the backend currently produces a coverage report
(`backend/coverage/lcov.info`, generated by `npm --prefix backend run
test:cov`). Frontend model tests run with `npm --prefix frontend test`, and
browser tests run with Playwright, but neither currently exports LCOV.
SonarQube still analyses frontend production code for bugs, smells and
duplication; frontend coverage remains unmeasured. Adding component coverage and pointing
`sonar.javascript.lcov.reportPaths` at both reports is the natural next step
when frontend LCOV coverage is added.
